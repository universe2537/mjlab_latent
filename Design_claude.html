1. 设计愿景与原则

我们追求的不是「能把球击回」的脚本动作，而是 具备网球比赛意义上「打球能力」的策略：能跑位、能击球、能选择落点、 能根据比分情境调整风险，并且动作姿态接近人类。

核心设计原则

  • 规则即环境：网球规则不是奖励工程的副产品，而是环境状态机的骨架。 得分、换发、终止都由规则机驱动，奖励只是稀疏信号的稠密化。
  • 分层解耦：低层负责「人形动作 + 球拍接触」，高层负责「跑位 + 落点 + 战术」。 两层通过明确接口通信，便于单独替换/迁移。
  • 对手即课程：对手（球的分发者）从「可预测发球机」逐步演化到 「自我对弈策略」，难度由数据驱动而非手工调参。
  • 可逆抽象：单打 / 双打 / 仅发球 / 仅接发，都是同一抽象在不同 规则配置 下的实例化，而不是各写一份环境。
  • 姿态可信：人类相似性通过 motion prior（参考动作分布）约束， 而不是把所有「像人」的行为写进 reward。

2. 网球规则的形式化

我们把网球规则压缩为强化学习需要的最小集合： 场地几何、击球合法性、回合结束条件、计分。

2.1 场地几何（单打）

元素 尺寸 RL 中的角色
球场长度 23.77 m 定义出界与底线区
单打宽度 8.23 m 定义边线
双打宽度 10.97 m 双打模式启用
球网高度 0.914 m（中心） 过网约束
发球区 对角 6.40 × 4.115 m 发球合法落点
底线 / 中线 / 边线 — 裁判判定的离散事件源

关键事件原子（events）：
ball_struck bounce_on_court bounce_out net_contact double_bounce racket_contact serve_fault point_won(side)

2.3 合法性判定（统一裁判函数）

裁判函数 Referee(state, events) → Verdict，输出三选一：
  • CONTINUE回合继续
  • FAULT本次发球失败（一发→二发，二发→失分）
  • POINT_END(winner)一分结束，进入计分子系统
裁判不依赖物理细节，只消费 事件流，因此可与任意物理后端解耦。

2.4 计分（嵌套有限状态机）

层级 状态 转移
Point 0 / 15 / 30 / 40 / Adv / Game 每分一次转移
Game 0–6（含 deuce/advantage） 赢一局后递增
Set 0–N（含抢七） 赢一盘后递增
Match 三盘两胜 / 五盘三胜 终止条件
RL 训练中通常 只跑到 Point 或 Game 粒度；Set / Match 用于评估。 计分 FSM 是奖励 shaping 的来源，但 不应 把分数差直接当 reward 主项。

3. 能力层级与课程

把「打网球」拆成可独立训练、可拼装的能力模块。每一层都是一个完整 MDP， 但共享物理与裁判抽象。

L0 — 运动基元

行走、跑动、转身、急停、挥拍轨迹。来自 motion tracking 的 latent space。

L1 — 接触技能

把球以期望速度/方向击出。给定球状态与目标击球点，输出动作序列。

L2 — 单球回合

给定来球，跑位 + 击球 + 落点选择，让对方无法回球或失误。

L3 — 发球

抛球 → 击球 → 落入对角发球区，含一发/二发风险权衡。

L4 — 多拍对抗

连续 N 拍中保持回球质量，引入对手反应。

L5 — 比赛策略

基于比分、对手习惯选择战术。可用 self-play 训练。

模块约定：L1 的输出接口（球的出射状态分布）就是 L2 的动作空间， L2 的输出接口（落点选择）就是 L5 的动作空间。这样可以用 hierarchical RL 或 distillation 把上层策略与下层策略解耦训练。

4.1 模块职责

模块 输入 输出 职责
Physics action state 仿真步进
EventDetector state, prev_state 事件流 把连续物理量转成离散事件
Referee 事件流 Verdict 规则裁定，无状态依赖物理
GameDirector Verdict reset / serve 信号 回合 / 局 / 盘调度
BallProvider director 信号 球初始/轨迹 对手抽象
RewardComposer state + 事件 + verdict scalar 稠密化稀疏胜负
TerminationComposer verdict + 安全检查 bool 软/硬终止
关键解耦：物理与规则之间隔着 EventDetector。 任何后端（MuJoCo、Isaac、真实硬件）只要能产出统一事件流，规则层就完全可复用。

5. MDP 形式化

5.1 观测空间（分组）

本体感知 (proprio)

  • 关节位置 / 速度
  • 根姿态、根线/角速度
  • 足底接触
  • 上一动作（动作平滑用）

球与场景 (exteroceptive)

  • 球相对位置 / 速度（机器人坐标系）
  • 球的预测落点（短时窗预测）
  • 球当前阶段（one-hot of ball state）
  • 距离边线 / 距离网的标量

任务上下文 (task ctx)

  • 本方/对方比分
  • 当前是发球/接发/对拉
  • 剩余发球次数（一/二发）
  • 目标落点提示（仅高层策略可见）

风格条件 (style cond, 可选)

  • motion latent（来自 tracking 教师）
  • 风格指令（正手 / 反手 / 截击）

5.2 动作空间（按层级）

层 动作语义 维度量级 频率
低层 关节目标位置 / PD target ~30 50–100 Hz
中层 motion latent z（由 tracking VAE 解码） ~32 25–50 Hz
高层 击球目标点 (x, y, 旋转, 弧高) ~4 每拍 1 次
推荐主训练形态：中层 latent + 高层目标点。 低层由已训练好的 motion tracking 策略提供，避免重复学习人形控制。

5.3 奖励组合（按事件类型分桶）

类型 奖励项 稠密/稀疏 说明
任务结果 赢得一分 稀疏 + 主信号
失分 稀疏 − 对称
合法过网且落界内 事件 + shaping
击球质量 球拍接触能量匹配 事件 + 避免「碰一下」
出射方向接近目标 事件 + 战术性
击球点在身体合理区域 事件 + 动作可信
移动 朝预测落点的接近 稠密 + 跑位 shaping
无效移动惩罚 稠密 − 能量项
姿态正则 motion prior log-prob 稠密 + 类人
关节限位 / 力矩 稠密 − 安全
失败安全 跌倒 / 越界 稀疏 − 硬约束

5.4 终止条件

硬终止 (terminated)

  • 机器人跌倒 / 自碰严重
  • 机器人越出场地外围安全区
  • 仿真发散（NaN）

软终止 (truncated)

  • 一分结束（POINT_END）
  • 一局 / 一盘结束（按训练粒度选）
  • 达到最大步数
区分 terminated / truncated 对 RL 至关重要：硬终止意味着「该状态没有未来价值」， 软终止仅是「episode 切片」，价值应 bootstrap。

6. 球的生成与对手模型

「球从哪里来」决定了任务难度和真实性。我们把球的来源抽象为 BallProvider 接口： 

class BallProvider:
    def reset(self, context) -> BallState: ...
    def respond(self, last_event, context) -> BallTrajectory | None: ...

6.1 Provider 谱系（按拟人化程度）

等级 Provider 行为 用途
P0 FixedSpawner 球以固定初始状态出现 L1 接触技能训练
P1 RandomFeeder 从分布中采样落点 / 速度 L2 单球回合
P2 BallisticOpponent 分析机器人位置后选择落点，球以解析弹道飞来 L4 多拍训练
P3 ScriptedAgent 简化人形对手 + 启发式策略 对抗课程
P4 SelfPlayAgent 另一份本策略的快照 L5 战术训练
P5 LeaguePlay 策略池 + 优先采样 避免循环克制
Provider 接口对外只暴露 球的轨迹/状态，不暴露对手的人形姿态。 这意味着即使没有第二个机器人，环境也能完整运行。对手的 visualization 是可选的渲染层。

6.2 发球的特殊性

  • 发球时球由 本方 持有，BallProvider 退化为 self-feed： 机器人需要先抛球（toss）再击球。
  • 必须落入对角发球区，否则 FAULT。
  • 一发追求威力，二发追求安全。可以用一个标量 risk ∈ [0,1] 作为高层动作的一部分，由策略学会权衡。

7. 得分系统与回合调度

7.1 ScoreState 数据结构

ScoreState:
  point:   {self: int, opp: int}      # 0/15/30/40/Adv
  game:    {self: int, opp: int}
  set:     {self: int, opp: int}
  server:  {self | opp}
  serve_count: 1 | 2                  # first / second serve
  side:    deuce | ad                 # 发球落点对角
  tiebreak: bool

7.2 GameDirector 主循环（伪代码）

loop:
    director.start_point()              # 决定 server / side
    ball_provider.reset(score_state)
    while not point_ended:
        action = policy(obs)
        state  = physics.step(action)
        events = detector(state)
        verdict = referee(events, score_state)
        reward = composer(state, events, verdict)
        if verdict == POINT_END(winner):
            score_state = score_fsm.update(winner, score_state)
            break
    if score_state.match_over: env.reset_match()

7.3 回合粒度选择

训练粒度 episode = ? 优点 缺点
Point-level 1 分 反馈快，方差小 缺战术上下文
Game-level 1 局 含发球切换 奖励更稀疏
Set-level 1 盘 战术信号充分 训练效率低，建议仅 self-play

8. 课程学习与难度旋钮

难度由一组 正交的旋钮 组成，由 curriculum manager 根据成功率自动调节。每个旋钮都对应规则或 BallProvider 的参数，不需要改动环境结构。

旋钮 低难度 高难度
来球速度 慢 专业速度
来球落点分布 身体附近 覆盖全场角度
来球旋转 无旋 上旋 / 切削
反应时间 提前可见 临近击球才可见
合法落点要求 整片半场 必须落入指定区域
多拍数 1 拍即终止 需连续 N 拍
对手类型 P0–P1 P4–P5
风格约束 无 必须正手 / 反手
课程进度由 多目标成功率向量 驱动，避免单一指标饱和。 推荐：每个旋钮独立维护成功率窗口，超过阈值后才提升对应难度。

9. 评估协议

训练奖励 ≠ 真实能力。设立独立的评估场景，跨多个维度打分。

9.1 评估指标

维度 指标
结果 赢分率、Ace 率、双误率
击球质量 过网率、落界率、出射速度分布
战术 落点熵、深球比例、角度覆盖
动作可信 motion prior 似然、跌倒次数、关节力矩 RMS
鲁棒 抗扰动成功率、对未见来球分布的迁移

9.2 标准评估场次

  • Drill：固定来球的接发，测量 L1/L2 能力。
  • Rally-N：与 P2 对抗 N 拍，测多拍稳定性。
  • Match：与 P3/P4 进行一局/一盘，测综合能力。
  • OOD：评估时使用训练未见过的旋转 / 风速 / 球速分布。

10. 扩展方向

双打模式

同侧两个 agent，引入合作维度。架构上只需： 场地宽度切换、Referee 增加双打边线、BallProvider 视为对方两人组合。

真实自我对弈

把 P4/P5 提升为完整双 agent 仿真。两个 policy 同步步进， Referee 视角对称化，奖励为零和。

视觉观测

把 ball state 替换为 egocentric 相机 + ball detector。 架构其余部分零修改，验证模块化的真正收益。

Sim-to-Real

EventDetector 改为消费真实传感器（球追踪 + IMU）， Referee 与 RewardComposer 完全复用。

总结：抽象层次

  1. 规则层（Referee + ScoreFSM）：与物理、机器人无关，纯逻辑。
  2. 事件层（EventDetector）：把物理量翻译成规则消费的语言。
  3. 调度层（GameDirector + BallProvider）：决定每个 episode 长什么样。
  4. 学习层（Obs / Action / Reward / Termination）：标准 RL 接口。
  5. 课程层：在以上四层之上调参，不改结构。

任何一层可以独立替换：换机器人只动 Physics；换裁判规则只动 Referee； 换训练目标只动 RewardComposer；换难度只动 Curriculum。这就是「打网球」 这件事被设计成可演化系统的方式。

1. mjlab 框架要点回顾

1.1 三层结构

  1. EntityCfg / SceneCfg：通过 spec_fn 构建 MuJoCo spec，多个 entity 拼接为一个 MjModel。
  2. ManagerBasedRlEnvCfg：声明式配置 {observations, actions, rewards, terminations, commands, events, curriculum}。每一项是 名字 → TermCfg 的字典。
  3. Manager：每步按字典顺序调用所有 term，把结果聚合为 obs dict / 标量 reward / done flag。

1.2 Term 的两种形态

形态 使用场景 例子
函数 无状态、纯计算 joint_pos_rel(env, asset_cfg)
类（继承 ManagerTermBase） 需要跨步状态、缓存、reset 钩子 LiftingCommand、MotionCommand

类形态有 __init__(cfg, env)、__call__(env, ...)、reset(env_ids) 三个钩子，是承载「规则 FSM」的天然位置。

1.3 框架对网球友好的特性

  • 多 Entity 场景：robot / ball / court 可独立建模（manipulation 已示范 cube）。
  • ContactSensor：原生支持几何对几何的接触力检测，是事件检测的关键基元。
  • CommandTerm 的状态化能力：tracking 的 MotionCommand 每步推进帧、维护 metrics、写入 sim，证明 CommandTerm 完全有能力承载复杂的「来球 + 规则 FSM」逻辑。
  • EventTerm 的 mode：startup / reset / interval / prestep 四种触发时机覆盖发球、重置、随机扰动等所有需求。
  • ActionTerm 可包装：Tennis 已有的 latent decoder 动作就是嵌套 JointPositionAction 的组合模式，可直接复用。

GameDirector 融合进 RallyCommand（episode = 一分）；跨 episode 状态由 EventTerm("score_bookkeeping", mode="reset") 维护 类 + 函数
RewardComposer rewards: dict[str, RewardTermCfg] 声明式
TerminationComposer terminations: dict[str, TerminationTermCfg]，区分 time_out=True（truncated）与默认（terminated） 声明式
Curriculum 旋钮 CurriculumTermCfg，操作 RallyCommand 的难度参数和奖励权重 类 + 函数
分层动作 ActionTermCfg：低层 JointPositionAction，中层 FrozenDecoderLatentJointPositionAction，高层 StrokeIntentAction（可选） 类
关键洞察：网球规则状态机不是 mjlab 缺失的概念，而是 CommandTerm 的天然实例。把 RallyCommand 当作「会观察物理、会写入物理、会报告 metrics」的有限状态机来写，整个规则层就落进了框架内，无需新增任何抽象。

5. CommandTerm：RallyCommand — 网球的中枢

核心设计：把球的生命周期 FSM、裁判逻辑、计分、来球生成全部封装在 一个 CommandTerm 里。它输出的「command」就是对策略可见的任务上下文（球状态阶段 + 比分 + 任务目标）。

# mdp/commands.py
@dataclass(kw_only=True)
class RallyCommandCfg(CommandTermCfg):
  ball_provider: BallProviderCfg     # 决定来球（P0~P5）
  rules: RulesCfg                    # 单/双打、有效区、二发开关
  scoring: ScoringCfg = field(...)   # point / game / set 粒度
  episode_granularity: Literal["point","game","set"] = "point"
  resampling_time_range = (1e9, 1e9) # 由 FSM 自驱，不让 manager 自动重采样
  def build(self, env): return RallyCommand(self, env)


class BallPhase(IntEnum):
  IDLE = 0
  SERVE = 1
  IN_FLIGHT = 2
  BOUNCED = 3       # 已合法落地一次，等机器人挥拍
  RETURN = 4        # 机器人已击出，飞向对方
  POINT_END = 5


class RallyCommand(CommandTerm):
  """规则 FSM + 球状态机 + 来球生成器，三合一。"""

  def __init__(self, cfg, env):
    super().__init__(cfg, env)
    self.ball   = env.scene["ball"]
    self.court  = env.scene["court"]
    self.robot  = env.scene["robot"]
    self.provider = build_provider(cfg.ball_provider, env)

    # 状态张量（per-env）
    self.phase         = torch.zeros(N, dtype=torch.long)   # BallPhase
    self.serve_count   = torch.ones(N, dtype=torch.long)    # 1 或 2
    self.score_point   = torch.zeros(N, 2, dtype=torch.long)  # [self, opp]
    self.last_event    = torch.zeros(N, dtype=torch.long)
    self.bounce_xy     = torch.zeros(N, 2)
    self.point_winner  = torch.full((N,), -1, dtype=torch.long)
    self.is_point_end  = torch.zeros(N, dtype=torch.bool)

    # metrics（自动记录到日志）
    self.metrics["aces"]          = torch.zeros(N)
    self.metrics["double_faults"] = torch.zeros(N)
    self.metrics["points_won"]    = torch.zeros(N)
    self.metrics["rally_length"]  = torch.zeros(N)
    self.metrics["over_net_rate"] = torch.zeros(N)

  @property
  def command(self) -> torch.Tensor:
    """暴露给 obs：one-hot phase + score + serve flag。"""
    return torch.cat([F.one_hot(self.phase, 6),
                      self.score_point.float() / 4.0,
                      self.serve_count.float().unsqueeze(-1)], dim=-1)

  def _resample_command(self, env_ids):
    """每分开始：让 BallProvider 把球放到合法位置。"""
    self.phase[env_ids]        = BallPhase.SERVE
    self.point_winner[env_ids] = -1
    self.is_point_end[env_ids] = False
    self.provider.spawn(env_ids, context=self._context(env_ids))

  def _update_command(self):
    """每个 env 步：消费事件流，推进 FSM。"""
    events = detect_events(self._env)            # 见 §6
    verdict = self._referee(events)              # CONTINUE / FAULT / POINT_END
    self._apply_verdict(verdict)
    self._update_metrics(events, verdict)
    self.provider.respond(events, self.phase)
    self.is_point_end = (self.phase == BallPhase.POINT_END)
为什么用 CommandTerm 而不是新建 Manager？
- CommandTerm 已有：观察 entity、写入 sim、per-env reset 钩子、metrics 上报、debug_vis、GUI 集成。
- command 属性天然成为 对策略可见的任务上下文向量，通过 mdp.generated_commands(env, command_name="rally") 就能注入 obs。
- 不破坏框架范式，不需要在 ManagerBasedRlEnv 里塞东西。

5.1 触发 episode 终止

RallyCommand 不直接调用 env.reset()。它只把 is_point_end 置位，由一个轻量 TerminationTerm 读取：

def point_ended(env, command_name="rally") -> torch.Tensor:
  return env.command_manager.get_term(command_name).is_point_end

terminations = {
  "point_end": TerminationTermCfg(func=mdp.point_ended,
                                  time_out=True,   # truncated, bootstrap value
                                  params={"command_name": "rally"}),
  ...
}

5.2 跨 episode 维持比分（Game / Set 粒度）

当训练粒度 = point 时，比分在 reset 时清零；当 = game / set 时，RallyCommand 在 reset() 里 不 清零比分，而是只清零本分相关字段。CommandTerm.reset(env_ids) 钩子完美契合。

class StrokeIntentAction(ActionTerm):
  """高层策略输出击球意图，由内部短期规划/学习的 mapping 转成 latent。"""
  action_dim = 4   # (target_x, target_y, arc_height, risk)
  def process_actions(self, a):

    z = self._intent_to_latent(a, self._env)
    self._mid_level.process_actions(z)
  def apply_actions(self):
    self._mid_level.apply_actions()

高层只在 击球前一刻 被调用一次（用 ActionTerm 的 update frequency 机制或简单的 phase gating）。低层每物理步运行。

9. CurriculumTerm：难度旋钮

课程的状态（当前难度等级）保存在 RallyCommand 内部张量；调度 由 CurriculumTermCfg 触发的函数完成。这两层正交。

# mdp/curriculums.py
def ball_speed_curriculum(env, command_name, success_metric, threshold):
  rally = env.command_manager.get_term(command_name)
  win_rate = env.metrics_manager.get_recent(success_metric, window=200)
  if win_rate > threshold:
    rally.provider.bump_difficulty("ball_speed")
  return float(rally.provider.difficulty["ball_speed"])

11. 与现有 tennis 实现的差异与迁移

维度 当前实现 建议演进
规则承载 分散在 rewards.py / terminations.py 的多个常量（SUCCESS_TARGET_LINE_X、VALID_HIT_MIN_*），每个 reward term 重复传 7~8 个参数 合并进 RallyCommand，常量收敛到 RulesCfg，term 只读 command 状态
球的来源 EventTermCfg("reset_ball", reset_root_state_uniform) —— 直接采样位置/速度，与规则无关 替换为 BallProvider 体系，第一步实现 RandomFeederProvider 作为现有行为的等价物
事件检测 每个 reward / termination 内部独立判断「是否击球 + 是否有效」（参见 hit_state.py） 抽取到 events.py，由 RallyCommand 统一消费、缓存到张量，下游纯查询
场地 court 已是独立 entity 给 court 加 语义 site（发球区中心、各边线），裁判函数通过 site 索引向量化判界，避免硬编码坐标
课程 未启用 引入 CurriculumTermCfg，让 BallProvider 暴露 bump_difficulty(key)
评估 play 脚本即评估 新增 scripts/evaluate.py，跑 Drill / Rally-N / Match 三套独立 task ID，输出 §9 指标
奖励复杂度 approach_ball_pre_hit 之类 term 同时承担「跑位」「击球时机」「失败惩罚」三件事，逻辑紧耦合 单一职责拆分：approach_predicted_landing（移动）+ contact_energy（击球）+ fault（事件）

11.1 迁移建议（最小破坏性顺序）

  1. Step 1：新增 events.py，把现有 hit_state.py 的判定逻辑抽出，不改任何配置。所有 reward term 改为读 events 缓存，行为等价。
  2. Step 2：新增 RallyCommand 与 RandomFeederBallProvider，先只承担来球生成，不接管规则。把 reset_ball 事件移除。
  3. Step 3：把规则常量 / 比分 / phase 迁入 RallyCommand，reward term 改为查询 command；策略不变，奖励数值不变。
  4. Step 4：实现 BallisticOpponentProvider，启用多拍课程。
  5. Step 5：开放 self-play / league。
迁移时关键：每一步保持训练曲线可对照。先用 RandomFeeder 复现当前性能，再叠加新规则。

结语

mjlab 提供的 EntityCfg、CommandTerm、ContactSensor、CurriculumTerm 已经是网球任务所需的全部基元。优雅实现的关键不是扩展框架，而是把网球规则状态机识别为一个 CommandTerm 实例，把对手识别为该 CommandTerm 的策略对象，把课程识别为对该对象的旋钮调度。

最终的 tennis 任务在框架内的形态与 tracking、velocity 一致：一个 base env_cfg + 一组 mdp/ 函数与类 + per-robot config。但其内部，通过单点封装（RallyCommand），承载了远比一般任务复杂的规则世界。这就是「优雅」在工程上的含义。
